# Наставник как настоящий агент: архитектура

> **Статус 2026-10-02.** Разделы 1–5 — исходный план. Его проверили 4 разных ИИ;
> итоговое решение с учётом их критики — в **разделе 6**, он главнее разделов 3–5
> там, где они расходятся. Шаги 1–3 из раздела 6 уже сделаны.

Документ — план перехода от «бота с уведомлениями + чек-инов Claude» к агенту,
который ведёт историю учёбы, помнит всё важное, сам замечает, что пора сказать,
и тратит токены только там, где нужна мысль, а не пересказ данных.

---

## 1. Что есть сейчас (честная диагностика)

**Источники (уже парсятся):** Modeus (расписание, оценки, посещаемость), LMS
(задания, оценки), Нетология (задания, вебинары, уведомления, записи вебинаров
→ транскрипты), LXP (через Modeus/yetanothercalendar), 2 почты (Яндекс,
Gmail), Мессенджер (ТюмГУ), ВК (беседа группы), yetanothercalendar (ссылки,
флаг LXP), сообщения пользователя боту, галочки в окне.

**Как это сейчас «помнится»:**

| Что | Где | Проблема |
|---|---|---|
| Задачи, расписание | `tasks.json`, `schedule_cache.json` | ок, детерминированно |
| Почта / мессенджер / ВК | `*_recent.json` (8 / 37 записей) | скользящее окно: старое **теряется навсегда** |
| Оргфакты из вебинаров | `study_knowledge.json`, 1814 фактов, 2,2 МБ | LLM читает файл целиком через Read — дорого и шумно |
| Память о человеке | `ai_memory_profile.txt` (2 КБ прозы) + `ai_memory_log.json` (16 заметок) | неструктурно, нет «обещаний», нет истории по предметам |
| Контекст дня | `claude_session.json` → `claude -p --resume` | каждый вызов пересылает **весь разговор дня** |
| Q&A | `mentor_qa_log.json` (20 последних) | отдельно от остальной памяти |

**Где сгорают токены (замер по журналам сессий за 24.09–01.10):**
- утренний чек-ин 08:30: 0,3–1,3 млн токенов (до 27 обращений к инструментам —
  модель сама бегает Read по сырым JSON);
- дневные/вечерние: 0,1–0,7 млн;
- выводы для окна: ~240 тыс. (уже убрано).

Корень проблемы: **LLM используется как парсер и как хранилище памяти**. Она
каждый раз заново читает сырые данные и заново «вспоминает» день целиком.
Настоящие агенты устроены наоборот: код знает факты, LLM получает маленький
отобранный контекст и только думает.

## 2. Как устроены настоящие агенты-помощники

Общий паттерн у зрелых систем (MemGPT/Letta, Mem0, ассистенты с долгой
памятью, «second brain»-агенты):

1. **Журнал событий (event sourcing).** Всё, что происходит во внешнем мире,
   нормализуется в один журнал: «новое письмо от преподавателя», «оценка 4 за
   лабу», «перенос пары», «пользователь сказал: сделаю в пятницу». Ничего не
   удаляется — только дополняется.
2. **Состояние выводится из журнала кодом.** Задачи, дедлайны, оценки,
   посещаемость — детерминированные проекции, без LLM.
3. **Иерархическая память:**
   - *рабочая* — что важно прямо сейчас (собирается кодом, 2–4 тыс. токенов);
   - *эпизодическая* — дневник: сжатые итоги каждого дня/недели;
   - *семантическая* — знания (оргфакты курсов, теория) с поиском;
   - *профиль/правила* — кто человек, как с ним говорить, его договорённости.
4. **Retrieval вместо «прочитай всё».** В промпт попадают только релевантные
   куски (по предмету, по дате, по смыслу).
5. **Инструменты вместо файлов.** LLM вызывает `get_course_status("БД")`,
   а не читает 2 МБ JSON. Записи (закрыть, напомнить) — только через код с
   подтверждением.
6. **Триггеры + решение «стоит ли говорить».** Агент не пишет по расписанию
   «потому что 14:00», а когда есть повод: новая оценка, риск по дедлайну,
   скоро пара, обещание не выполнено, давно тишина. Расписание — лишь
   страховка.
7. **Рефлексия.** Раз в день/неделю агент сжимает события в дневник,
   обновляет профиль и проверяет свои прошлые прогнозы.
8. **Бюджет и маршрутизация моделей.** Дешёвая модель — извлечение и сжатие,
   умная — разговор и недельный разбор. Учёт токенов на каждый вызов.

## 3. Целевая архитектура

```
 ┌──────────── Источники ────────────┐
 │ Modeus  LMS  Нетология  LXP  Почта×2│
 │ Мессенджер  ВК  вебинары  бот/окно  │
 └───────────────┬────────────────────┘
                 ▼  (парсеры как сейчас, + нормализация)
        ┌─────────────────────┐
        │ 1. EVENT LOG (SQLite)│  append-only, dedup по хэшу
        └─────────┬───────────┘
      код ▼                     ▼ Haiku (дёшево, по событию)
 ┌──────────────────┐   ┌───────────────────────────┐
 │2. STATE (проекции)│   │3. ИЗВЛЕЧЕНИЕ              │
 │ задачи, пары,     │   │ факты, обещания, риски,   │
 │ оценки, посещ.,   │   │ «требует ответа» из писем │
 │ статус по курсам  │   │ и чатов → в память        │
 └────────┬─────────┘   └──────────┬────────────────┘
          ▼                        ▼
 ┌─────────────────────────────────────────────┐
 │4. ПАМЯТЬ                                     │
 │ profile.md · commitments · diary(дни/недели) │
 │ course_notes (по предмету) · knowledge+FTS   │
 └────────────────────┬────────────────────────┘
                      ▼
 ┌─────────────────────────────────────────────┐
 │5. ТРИГГЕРЫ + ПРАВИЛА (код)                   │
 │ salience-скоринг, тихие часы, бюджет токенов │
 └────────────────────┬────────────────────────┘
                      ▼ только если есть повод
 ┌─────────────────────────────────────────────┐
 │6. AGENT CALL (Sonnet)                        │
 │ context pack ≤ 8–12k токенов + MCP-инструменты│
 └────────────────────┬────────────────────────┘
                      ▼
       Telegram (разговор) · окно на столе (состояние)
```

### 3.1 Event log — `data/agent.db` (SQLite)

```sql
CREATE TABLE events (
  id        INTEGER PRIMARY KEY,
  ts        TEXT NOT NULL,          -- когда произошло (UFA_TZ, ISO)
  source    TEXT NOT NULL,          -- modeus|lms|netology|lxp|mail_yandex|mail_gmail|messenger|vk|webinar|user|widget|system
  kind      TEXT NOT NULL,          -- task_new|task_deadline_changed|task_done|grade|attendance|lesson_moved|message|mail|webinar_fact|user_said|reminder_fired|...
  course    TEXT,                   -- нормализованное имя курса (справочник courses)
  title     TEXT,
  body      TEXT,                   -- полный текст (письма/сообщения — не обрезать)
  url       TEXT,
  ref_id    TEXT,                   -- id задачи/письма во внешней системе
  importance INTEGER DEFAULT 0,     -- выставляет код/Haiku: 0..3
  hash      TEXT UNIQUE             -- dedup
);
CREATE VIRTUAL TABLE events_fts USING fts5(title, body, content='events', content_rowid='id');
CREATE TABLE courses (id TEXT PRIMARY KEY, name TEXT, aliases TEXT, teacher TEXT, grading TEXT);
```

- Каждый парсер, помимо текущих JSON (их не ломаем — бот и окно на них живут),
  пишет события в журнал через одну функцию `record_event(...)`.
- `*_recent.json` перестают быть единственным хранилищем: история писем и
  чатов больше не теряется.
- Справочник `courses` с алиасами решает вечную проблему «Базы данных» vs
  «3 семестр: Базы данных» vs «БД».

### 3.2 State — детерминированные проекции (код)

Уже частично есть (`mentor_dashboard.py`). Добавить `course_status(course)`:
дедлайны, просрочки, последние оценки, посещаемость, ближайшие пары/вебинары,
непрочитанные важные письма по предмету, «риск» (формула: просрочки ×
вес оцениваемости + пропуски + близость сессии).

### 3.3 Извлечение (Haiku, по событию, дёшево)

На каждое новое письмо/сообщение/объявление — один короткий вызов Haiku
(~1–2 тыс. токенов) с жёсткой JSON-схемой:

```json
{"needs_reply": true, "deadline_mentioned": "2026-10-10", "course": "БД",
 "facts": ["Преподаватель перенёс сдачу лабы 3 на 10.10"],
 "commitments": [], "importance": 2}
```

Факты → `course_notes`, сроки → предложение задачи (с подтверждением в боте),
`needs_reply` → список «ждут ответа».

### 3.4 Память

| Слой | Файл/таблица | Кто пишет | Размер в промпте |
|---|---|---|---|
| Профиль | `memory/profile.md` (разделы: цели, как говорить, что мотивирует, правила) | недельная рефлексия + явные «запомни» | ≤ 1,5k |
| Договорённости | `commitments` (что/к какому сроку/статус/источник) | извлечение из твоих сообщений («сделаю в пятницу») | только открытые, ≤ 1k |
| Дневник | `diary` (день → 5–10 строк, неделя → 10–15) | ночной Haiku-вызов по событиям дня | последние 3 дня + неделя, ≤ 2k |
| Заметки курса | `course_notes` (по курсу: требования, договорённости с преподом, история оценок) | извлечение + рефлексия | только релевантные курсы, ≤ 2k |
| Знания | `study_knowledge` → таблица + FTS5 (позже — эмбеддинги) | как сейчас | топ-k по запросу, ≤ 2k |
| Диалог | последние 10–20 реплик с ботом | бот | ≤ 2k |

Главное: **дневная сессия `--resume` заменяется на context pack**. Связность
между вызовами обеспечивают дневник + последние реплики, а не пересылка всего
разговора.

### 3.5 Триггеры и «стоит ли говорить»

Код каждые N минут считает поводы со скорингом:

| Повод | Пример | Вес |
|---|---|---|
| Новая оценка / посещаемость | 2 за лабу | высокий |
| Риск дедлайна | оцениваемое, ≤ 2 дня, не начато | высокий |
| Обещание просрочено | «сделаю лабу в пятницу», пятница прошла | высокий |
| Письмо ждёт ответа > 24 ч | от преподавателя | средний |
| Перенос/отмена пары | ВК, Modeus | средний |
| Скоро пара | за 60/15 мин | без LLM, шаблон |
| Тишина | 2 дня без активности | низкий |

Правила: тихие часы, не больше X сообщений в день, группировка поводов в одно
сообщение, дневной бюджет токенов. Утренний бриф и вечерний итог — остаются
как плановые, но собираются из context pack. Дневные «пинги ради пингов» —
убрать, вместо них — сообщения по поводу.

### 3.6 Agent call

- Модель: Sonnet для разговора/брифов/недели, Haiku для извлечения/дневника.
- Промпт: статичный префикс (персона + правила, кэшируется) + context pack.
- Инструменты (MCP-сервер проекта или узкий CLI), а не Read по файлам:
  `get_today()`, `get_course_status(course)`, `search_knowledge(q, course)`,
  `search_history(q, since)`, `list_commitments()`, `propose_task(...)`,
  `propose_reminder(...)` — **propose** = бот покажет кнопку подтверждения,
  сама модель ничего не пишет (сохраняем текущую границу безопасности).
- Учёт: каждый вызов логирует `usage` в `agent_calls` (токены, модель,
  триггер) → недельный отчёт расходов.

### 3.7 Рефлексия

- **Каждую ночь (Haiku):** события дня → запись дневника; закрыть/обновить
  обещания; отметить, что предсказывал вчера и что вышло.
- **Каждое воскресенье (Sonnet, один вызов):** недельный разбор + обновление
  `profile.md` и `course_notes` (диффом, с историей версий), план на неделю.

## 4. Бюджет: было → станет (оценка)

| Вызов | Сейчас | После |
|---|---|---|
| Утренний бриф | 0,3–1,3 млн | ~12–15 тыс. |
| Вечерний итог | 0,1–0,7 млн | ~12–15 тыс. |
| Сообщение по поводу | — | ~8–12 тыс., 0–3 в день |
| Извлечение письма/сообщения | — (не делается) | ~1–2 тыс. Haiku × N |
| Дневник (ночь) | — | ~5–10 тыс. Haiku |
| Неделя | ~0,5–1 млн | ~30–40 тыс. |

Порядок: **с ~1–3 млн токенов в день до ~60–120 тыс.**, при этом памяти больше.

## 5. План внедрения (по шагам, каждый полезен сам по себе)

1. **Event log + `record_event`** во всех парсерах; справочник курсов.
   Ничего не ломает, история перестаёт теряться.
2. **Context pack** (`agent/context.py`): код собирает сводку дня + курсы
   + последние реплики. Перевести чек-ины на него, убрать `--resume`.
   Самая большая экономия сразу.
3. **Дневник + обещания** (ночной Haiku, извлечение из сообщений боту).
4. **Извлечение из почты/чатов/ВК** (Haiku по событию) → «ждут ответа»,
   факты курса, предложения задач.
5. **Триггеры по поводу** вместо части плановых чек-инов.
6. **MCP-инструменты** для свободных вопросов в боте (вместо Read по JSON).
7. **Поиск по знаниям** (FTS5 → при необходимости эмбеддинги).
8. **Недельная рефлексия** с обновлением профиля и курсовых заметок.

Принципы, которые нельзя нарушать (выведены из реальных ошибок проекта):
- списки и даты строит код, не LLM;
- запись в данные — только кодом и с подтверждением пользователя;
- Modeus и Нетология — разные занятия, не дедуплицировать;
- напоминание исчезает только когда пользователь сам его закрыл;
- дата события ≠ время напоминания;
- проверять вживую, а не только чтением кода.

## 6. Итоговое решение после ревью (4 ИИ)

### В чём все четверо согласны
- Главная экономия — **context pack вместо `--resume` дневной сессии**, делать первым.
- Списки, даты, статусы — код; LLM только формулирует и приоритизирует.
- **FTS5 + фильтры по курсу/дате** хватает на этом масштабе; эмбеддинги — только после
  измеренного провала FTS на реальных вопросах.
- **CLI/Python-функции, не MCP** — пока нет второго клиента и > 8–10 инструментов.
- Выводы модели ≠ факты: всё, что извлекла модель, — **кандидат** до подтверждения.
- Обещания создаются только после кнопки «Да» в боте, с цитатой-основанием.
- Скоринг «говорить/молчать» — кодом, сначала в теневом режиме (логировать, не слать).
- Сначала мерить (журнал вызовов), потом оптимизировать.

### Где мнения разошлись и что выбрано
| Вопрос | Мнения | Решение |
|---|---|---|
| Event sourcing целиком | 3 ИИ: избыточно; 1: «единственно верный путь» | **Гибрид:** неизменяемый `raw_events` + обычные изменяемые таблицы; состояние не восстанавливаем проигрыванием событий |
| Отдельная таблица обещаний | 1 против (kind в events), 3 за | **Отдельная `commitments`** — нужны статусы candidate/open/done и подтверждения |
| Модель для обещаний и дневника | 1: только Sonnet; 3: Haiku + подтверждение | **Haiku** после regex-фильтра; ошибка не страшна, т.к. всё подтверждается кнопкой |
| Эмбеддинги для оргфактов | 1 за (синонимы «JOIN» ↔ «соединение»), 3 против | **Нет пока.** Синонимический словарь курсов/терминов; вернуться, если FTS промахивается |
| Бюджет context pack | 2–5k / 8–12k / 0,6–1k | Профили: шаблон без LLM — 0; по поводу — 1–2k; вопрос — 3–6k; бриф — ≤ 6k данных |
| Ночная рефлексия правит профиль | все против автоматической перезаписи | `memory_claims` со статусами; `profile.md` — **генерируемое представление** подтверждённых записей |

### Поправки к схеме данных (из ревью)
- Время: `occurred_at` / `observed_at` / `effective_at` / `ingested_at` — иначе вернётся
  ошибка «дата события ≠ время напоминания».
- Дедупликация: `UNIQUE(source, kind, external_id, payload_hash)`; изменение дедлайна —
  **новая версия** того же объекта, а не новый объект.
- SQLite: WAL, `busy_timeout`, короткие транзакции, одна функция записи, `schema_version`,
  бэкап перед миграцией; права файла `0600` (там будет личная переписка).
- FTS5 external content требует триггеров синхронизации.
- «Ничего не удаляется» — неверно для личных данных: нужна возможность удалить/исправить факт.

### Минимальные таблицы
`raw_events`, `courses` (алиасы), `commitments`, `memory_claims`, `notification_state`
(last_sent / acknowledged / dismissed / snoozed_until), `dialog_messages`, `agent_calls`.
Дневник, заметки курсов и профиль — представления, а не источники истины.

### Скоринг (стартовая версия, калибровать по журналу)
```
score = base_reason + urgency(0..25) + importance(0..15) + actionability(0..10)
        + novelty(0..10) − repetition(0..50) − quiet_hours(0|100)
≥ 75 → сразу · 45–74 → в ближайший бриф · < 45 → молчать
```
Лимиты: ≤ 2–3 инициативных сообщения в день сверх брифов; один fingerprint — не чаще
раза в 24 ч; после игнора интервал растёт; «тишина 2 дня» выключена по умолчанию.
Шаблонные уведомления (скоро пара, напоминания) — кодом, без LLM.

### Порядок внедрения
1. ✅ **Журнал вызовов** `data/agent_calls.jsonl` — каждый вызов Claude: цель, модель,
   токены, длительность (`claude_session.log_agent_call`).
2. ✅ **Context pack** из существующих JSON — `scripts/mentor_context.py`
   (блоки по слоту, ≤ ~3 тыс. токенов данных).
3. ✅ **Чек-ины без `--resume`** — `run_claude_oneshot`, без инструментов; связность —
   через `data/mentor_sent.json` (что уже писал) + память прошлых дней.
   Замер на утреннем: **~19 тыс. токенов вместо 0,3–1,3 млн**.
4. Неделя наблюдения по `agent_calls.jsonl`; кнопки 👍/👎 под сообщениями наставника.
5. SQLite `raw_events` — сначала сообщения пользователя боту и почта.
6. FTS5 + простой CLI поиска (`agent search …`) для ответов на вопросы.
7. `commitments` — кандидаты из сообщений боту, только с подтверждением.
